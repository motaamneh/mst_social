# Following a request through MST Social

The server logs lifecycle events, outcomes, and timings. Start with the HTTP
response's `X-Request-Id` header, then search for that value in the server logs.
This is a fresh UUID generated by the server for each API request. It is separate
from a verification's `requestId`, which is logged as `verificationId`.

## Enable more detail in IntelliJ

In **Run → Edit Configurations → MstSocialApplication → Environment variables**, add:

```dotenv
MST_LOG_LEVEL=DEBUG
```

Rebuild and restart the application. A running Java process does not automatically
load changed code or environment variables. Logs appear in that process's **Run**
console. Use `INFO` for normal operation; DEBUG adds troubleshooting detail.

For Docker, put the same setting in `.env.docker`, then apply it:

```sh
docker compose --env-file .env.docker up --build -d --wait
docker compose --env-file .env.docker logs -f app
```

Docker logs belong to the container, not a separate IntelliJ Run console.

## Levels and events

| Level | Events |
| --- | --- |
| INFO | HTTP success summaries; verification creation and success; cancellation/revocation results; successful provider fetches; credential creation/revocation metadata |
| WARN | HTTP 4xx summaries; rejected credentials; validation errors; rate limits; unsuccessful verification outcomes and expected provider failures |
| ERROR | HTTP 5xx summaries; storage errors; unexpected application/provider exceptions |
| DEBUG | Request/attempt starts; authentication success; status reads; transaction completion and timing |

The `event` field is a stable search label. Other fields explain what happened:

| Event | Useful fields |
| --- | --- |
| `http.request.started` | `method`, `route` |
| `http.request.completed` | `method`, `route`, `status`, `durationMs`, `completedNormally` |
| `authentication.failed` | `reason`, and safe exception metadata for storage failures |
| `authentication.succeeded` | Authenticated `tenantId` and `credentialId` in log context |
| `verification.created` | `verificationId`, `platform`, `expiresAt` |
| `verification.started` | `verificationId` |
| `verification.read` | `verificationId`, `state`, `failedAttempts` |
| `verification.completed` | `verificationId`, `outcome`, `state`, `failedAttempts`, `maxFailedAttempts`; account or provider-failure metadata when applicable |
| `verification.cancel.completed` | `verificationId`, resulting `state` |
| `account.read` | `accountId`, `active` |
| `account.revoke.completed` | `accountId`, `active`, `revokedAt` |
| `provider.fetch.started` | `provider`, `platform` |
| `provider.fetch.completed` | `provider`, `platform`, `durationMs`, `outcome`; `reason`, `retryable`, `retryAfter` on failure |
| `provider.fetch.failed` | Unexpected exception type/location, provider, platform, duration |
| `validation.failed` | `code`, known invalid field names; never submitted values |
| `rate_limit.exceeded` | `operation`, `limitPerMinute`, `retryAfterSeconds` |
| `api.operation.rejected` | HTTP `status`, stable error `code` |
| `http.request.rejected` | Framework HTTP error, e.g. malformed JSON; status/code and safe exception metadata |
| `storage.transaction.completed` | `committed`, `durationMs` |
| `storage.failed` / `application.failed` | Exception type, first application source location, SQLSTATE when available |
| `credential.created` | Tenant ID, credential ID, optional expiry; never the credential secret |
| `credential.revoke.completed` | Tenant ID, credential ID, whether a row changed |

`completedNormally=true` means the filter chain returned normally. A handled 401,
422, or 500 can still have that value. Inspect `status` to determine HTTP success.
An unsuccessful transaction may be an expected domain rejection, such as an active
request conflict; it does not by itself establish a database outage.

## Diagnose a 401

The API deliberately returns a generic `UNAUTHORIZED` response. Server logs give
operators a more specific reason without exposing that distinction to callers:

| Reason | What to check |
| --- | --- |
| `MISSING_OR_INVALID_AUTHORIZATION_HEADER` | Missing Bearer header, duplicate Authorization headers, incorrect total length, or wrong scheme |
| `MALFORMED_CREDENTIAL` | Token does not have the expected `mst_api_<uuid>.<secret>` format |
| `UNKNOWN_CREDENTIAL` | Credential ID is absent from the connected database; check CLI/server database configuration |
| `SECRET_MISMATCH` | Wrong credential secret or different `MST_TENANT_API_KEY_HASH_KEY` between provisioning and server |
| `REVOKED_CREDENTIAL` | Generate/use an active credential |
| `EXPIRED_CREDENTIAL` | The credential reached its configured expiry |
| `NOT_YET_ACTIVE` | Creation timestamp is in the future; check clocks/data |
| `STORAGE_UNAVAILABLE` | Credential lookup failed; the API returns 503, not 401 |

If a token has the wrong length, the header filter rejects it before the credential
parser. The reason is therefore about header format, even when the Bearer prefix exists.

## Follow a verification

With DEBUG enabled, an eligible verification request normally produces:

```text
http.request.started
authentication.succeeded
verification.started
storage.transaction.completed
provider.fetch.started
provider.fetch.completed
storage.transaction.completed
verification.completed
http.request.completed
```

Use their shared `httpRequestId` to join the lines. Provider fetch timing is separate
from the total HTTP duration and transaction timings. A provider call can return
`FOUND` while verification returns `CODE_NOT_FOUND`: fetching the profile succeeded,
but the required code was absent. Already verified, canceled, locked, or expired
requests can finish without a provider call. Rate-limited requests stop earlier.

Cancellation/revocation logs describe the resulting state. They do not claim that
every repeated request changed a row. Mutation success events run after the core
service returns, following its database commit.

## JSON output

The default console output is readable text with event fields and request/tenant
context. Set these environment variables for machine-readable JSON:

```dotenv
MST_LOG_LEVEL=INFO
MST_LOG_FORMAT=logstash
```

Recreate the Docker container or restart IntelliJ after changing them. Leave
`MST_LOG_FORMAT` empty to return to text. Spring Boot's structured logger includes
the event key/value fields and MDC context as JSON properties. See the
[Spring Boot logging documentation](https://docs.spring.io/spring-boot/reference/features/logging.html).

## What gets logged and what stays private

Our application events include opaque tenant, credential, verification, and account
UUIDs when relevant. These identifiers help operators investigate problems; restrict
access to logs and choose retention appropriate to your deployment.

These events exclude:

- Authorization headers, API credentials, passwords, hash keys, and digests.
- Verification codes, request/response bodies, social biographies, handles, and subject IDs.
- Raw request paths, query strings, provider URLs/payloads, and SQL/bind values.
- Raw exception messages and cause stack traces, which can contain submitted data.

Exception diagnostics instead include the exception class, an application code
location when available, and a validated SQLSTATE when present. This is a deliberate
tradeoff: some failures may need reproduction in a controlled environment for deeper
debugging. No global SQL, HTTP-client wire, or Spring TRACE logging is enabled here.
Third-party startup diagnostics have their own logging behavior; this policy describes
the application events added by MST Social.

The request logger covers synchronous `/api/v1` requests that enter the security
chain, including authentication failures. Health and Swagger assets are excluded.
Malformed HTTP rejected before that chain is outside its scope. Incoming
`X-Request-Id` values are not trusted or echoed: the server always generates its own.

## How the code works

- `ApiRequestLoggingFilter` wraps authentication/controllers, sets `X-Request-Id`,
  measures elapsed time, and restores the previous MDC context in `finally`.
- MDC is per-thread logging context. Clearing/restoring it prevents reused servlet
  threads from accidentally attributing the next request to the previous tenant.
- Authentication adds tenant/credential UUIDs only after successful validation.
- Controllers and the HTTP mapper log workflow results without serializing domain objects.
- `LoggingProfileProvider` wraps the provider bean and times the synchronous call.
  The underlying SearchAPI bean retains its own lifecycle/close handling.
- `SafeExceptionDetails` extracts bounded, safe diagnostics without logging a Throwable.
- The core and provider libraries acquire no new logging or Spring dependencies.

These logs support troubleshooting; they are not a durable audit ledger or a
distributed tracing implementation. MDC does not automatically cross arbitrary
async executor boundaries. The current synchronous provider wrapper logs before
and after its call on the request thread.

## Verification performed

On 2026-10-19, Maven packaging and the Docker build passed with
`-Dmaven.test.skip=true`. Manual requests against a disposable isolated database
covered missing credentials (401), valid credentials (200), creation (201), invalid
input (400), status reads (200), cancellation (200), and attempting an already
canceled verification (409). The last operation made no provider call.

Inspected JSON/DEBUG and text/INFO output, response/log request-ID correlation,
ignored caller-supplied correlation IDs, and absence of tenant context on a later
unauthenticated request. The checked log did not contain the temporary credential,
returned verification code, submitted handle, or subject ID.

No automated test files were created and no automated tests ran. No live SearchAPI
call or forced database outage was used, so provider and outage log paths were
reviewed in code rather than exercised against those external services.
